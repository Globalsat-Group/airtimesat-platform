**Changes of 20 Oct 2026 (CTO decisions after the first review).**

1. **Hosting for S2 is one VM outside AWS** (SITEST only). DigitalOcean is the reference provider, because Globalsat's Hub already runs on one DigitalOcean droplet with Docker Compose; Hetzner is the alternative. Docker Compose runs separate containers: the masker, a signer that alone holds the SITEST secret, and Postgres, with Caddy for TLS. A provider cloud firewall and a host firewall allow inbound 443 only, plus admin access from the CTO only, and outbound only to SITEST on 8443 plus DNS, NTP and package and image registries (§3.2 narrows this further). Static public IP. The CTO's target is about US$12–25/month; the DigitalOcean reference at the recommended size comes to about US$24–31 and Hetzner to about US$10–15 (*Inferred*, §14.2). See §3, §14.
2. **The S2 masker uses no AWS service.** KMS, Secrets Manager, IAM roles, the ALB, the NAT gateway, VPC endpoints, RDS, CloudWatch and Session Manager are replaced by VM controls: sops-encrypted, root-only secret files injected only into the container that needs them; signing and masking keys held the same way, with the CTO's Keeper as key custody and a defined trusted machine for the private keys (§13.4); SSH with hardware-backed keys only, for the CTO only (§17 #16); encrypted backups; automatic security updates; local logs, host security logs shipped to an append-only bucket, and an alert channel. No AWS key is ever placed on the VM. See §3, §6.3, §8, §9, §11.4, §13, §14.
3. **One IWS test user.** No second user is requested. The masker makes Beta unreachable on its own side, holds at most 1 of the user's 2 concurrent request slots so the CTO's own live runs keep the other, and pauses agents automatically during the CTO's dry runs and the certification run. See §9, §10, §13.3.
4. **S2 is re-baselined with the same scope** and the S2a/S2b split kept (§16).
5. **Departure from re-plan §3.4, for S2 only.** The re-plan put the masker in Globalsat's AWS account next to the gateway. The CTO changed that for S2. The production gateway (S4) stays in AWS, and its hosting details are decided then.
6. **§17 recommendations are accepted decisions**, updated for the VM. Items that still need the CTO, the new data-protection point for the hosting provider, and the choices the security review of the VM design raised are marked **Open** in §17.

Conventions: *Inferred* marks an estimate or a design choice with no calibrated source. "Uncertain" marks something the sources do not settle. Every example value is fake and shows the surrogate format, never a real identifier.

## 1. Goal, scope and non-goals

**Goal.** Let AI agents run and debug IWS calls against SITEST without ever seeing a real identifier, holding an IWS secret, reaching Beta or production, or writing outside a CTO-approved test plan. The masker is the only path from agents to SITEST (re-plan §3.4). SITEST is refreshed from production, so it is treated as production personal data (Phase 1 plan §0, finding 8; §4.2).

**What S2 delivers.**

| Part | S2a: read path (opens agents for S3) | S2b: write guard (before ST-04) |
|---|---|---|
| Agent endpoint | HTTPS, CTO-minted session tokens (§3) | Same |
| Method policy | Read allowlist; always-refused list; default deny (§4) | Plan-gated write allowlist; DEACTIVE hard block (§8) |
| Masking | Consistent pseudonymization of every identifier in every allowed response (§5, §6) | Unmasking of identifiers in write requests, scoped to test inventory (§7) |
| Recorder | Call log of every agent call, masked only (§9) | Same, plus plan and idempotency records |
| Concurrency | One IWS permit at most, shared permit ledger (§10) | Same |
| Leak gate | Detectors, per-shape tests, fixture scan, runtime block and alarm (§11) | Request-side detector for writes |
| IWS access | The gateway signer core, built in S2 and run as a separate signer container, reached through `gateway.sitest_port` (§12) | Same |
| Infrastructure | One VM: a provisioning script and a Compose file, never run by agents (§14) | Same |

The re-plan's S2 exit is unchanged: leak tests green on recorded samples, and the CTO has reviewed the code line by line (§15). This design splits S2 in two so agents can start read-only S3 work as soon as S2a passes. S2b must pass before ST-04 (polymorphic write and the SBD lifecycle, Annex F §7.2), the first spike test that writes.

**What waits for S3 or later.** The full operation registry for all 177 methods and the CI rule on unclassified WSDL operations (Annex D §2.1); the typed client and xsdata bindings (ST-01); lanes, aging, breaker and fault normalization (Annex D §2.4–2.7); the gateway service itself and its production endpoint (S4); HA (deferred, D2); the evidence module (S4); masking of raw-usage rows and inline report rows (§17 #6); the spike-test harness (§12.4, §17 #18).

**Non-goals.** No production. No Beta, ever (Beta is CTO-only; CTO decision, 20 Oct 2026). No DEACTIVE through the masker. No real CDRs, TAP files or customer exports. No unmasking service for agents. No bulk export of SITEST data (enforced by row caps and daily budgets, §4.2, §10). No UI. No HA.

## 2. Threat model

### 2.1 Assets

| Asset | Why it matters |
|---|---|
| SITEST IWS secret | One development credential covers SITEST **and Beta** (decision, 20 Oct 2026). A leak of the SITEST secret is also a leak of Beta access. Iridium's rotation procedure and lead time are not known yet (re-plan §11.1 Q4; Annex B Q24). |
| Personal data in SITEST | A copy of production: IMEI, ICCID, IMSI, MSISDN, names, emails, vessel contacts, locations (Phase 1 plan §4.6, "Personal data and PIN"). |
| Write capability | Writes change SITEST state. DEACTIVE is irreversible: SIMs are not recycled, MSISDNs and IPs go into 60-day quarantine (catalog `overview_workflows_rules.md`, Rules). Test inventory is scarce: about 3 full runs are requested (re-plan §11.1 Q10). Some writes act on every matching contract in the SP (`manageDestinations`; Phase 1 plan §4.6). |
| The two IWS permits | A third concurrent request is rejected (catalog Rules; Annex D §2.4). Agent load can starve the CTO's own calls or a certification dry run. |
| Masking keys and the vault | The vault maps surrogates back to real values. Whoever reads it can de-pseudonymize everything agents have seen. Numeric types have little entropy (an IMEI with a known TAC has about 10^6 candidates, *Inferred*), so `K_mask` alone lets an attacker rebuild their mapping by brute force: a `K_mask` compromise equals a vault compromise for those types. |
| IWS signatures | The signature covers only the operation name and the timestamp (catalog signature algorithm). A leaked (operation, timestamp, signature) triple can be replayed with any body against SITEST or Beta within IWS's clock-skew tolerance, which is still unknown (Annex D open questions). |
| Agent session tokens | A token grants masked reads, and plan-scoped writes, until it expires. The agent proxy terminates TLS, so the token and masked data are visible to the proxy layer. |
| Recordings and call log | Masked, but still pseudonymized personal data while the vault exists. Agent transcripts held by the agent provider contain masked data too (§9). |
| Certification evidence | The evidence must match the `getIwsRequests` extract one to one (Annex E §2.3). Agent calls mixed into a certification window would break that. |

### 2.2 Actors and what each failure would leak or break

| Actor | Can do | Worst outcome without controls | Controls (section) |
|---|---|---|---|
| **Honest agent** (bugs, loops, misunderstandings) | Call allowed methods with a valid token | A wrong write on the wrong line; permit starvation; a masked fixture that still holds a real value committed to git | Plan-gated writes, dry run, idempotency (§8); rate limits and one permit (§10); fixture scan and runtime detector (§11) |
| **Prompt-injected agent** (instructions hidden in a repository, a web page, or a free-text field in SITEST data such as a vessel name or `spReference`) | Anything its token allows, chosen by the attacker | Exfiltrating real identifiers by enumeration or echo; DEACTIVE; SP-wide writes; reaching Beta | Vault-only unmasking; guesses alarm and daily budgets cap reads (§6, §7, §10); request-side detector (§11); always-refused list and hard blocks in code (§4, §8); no Beta endpoint anywhere the masker can load (§13); free text is tokenized as a whole value unless it matches a reviewed template (§6.1), which also removes most injection text |
| **Compromised agent session** (an attacker holds the session and its token) | Same as above, until the token expires or is revoked | Masked data for up to the token lifetime, within the token's read scope and daily budgets; writes inside one approved plan | Short tokens (§17 #12), revocation and kill switch (§3, §14); read scopes and budgets (§3.3, §10); no IWS secret or cloud credential in the session; writes need a plan the CTO signed (§8) |
| **Compromised masker process** (an exploit in XML parsing, or a malicious dependency) | Whatever the masker container can do | The vault and masking keys; SITEST reads through the signer, within one permit; writes only inside an approved plan's signed test inventory, because the signer checks write scope itself; it cannot read the SITEST secret without a container escape (the masker container never holds it) | The masker container has no egress at all: it sits only on internal Docker networks (§3.2); the signer container alone holds the secret, accepts calls only from the masker with the link token, re-checks the allowlist, the DEACTIVE and bulk blocks, plan scope, signed inventory, the write budget and the pause flags, and never returns the signature (§12.1); the masker runs under gVisor (§14.1); no shared host, database or role with anything that holds a production credential (§3.1); reviewed images pinned by image ID (§14.3) |
| **Compromised caddy** (an exploit in the TLS and HTTP front end) | Whatever the caddy container can do | Every token and masked response that passes through it while it is compromised | Bounded by token lifetime, read scopes, daily budgets and plans (§3.3, §10); admin API off, gVisor, no direct egress: at most the ACME certificate authority through the egress proxy (§14.1, §14.3, §17 #11) |
| **Root on the VM** (a container escape, a stolen SSH key, the provider console) | Everything on the running VM | Everything: the SITEST secret (and so Beta access), `K_mask`, the vault key, the database passwords, every decrypted secret file; it also controls the code that checks tokens and plans, so it never needs to forge one | FIDO2 SSH opened per session and provider guest agents removed (§14.1); gVisor, distinct UIDs, seccomp and AppArmor (§14.1); patching with a 72-hour reboot rule (§14.1); host events and security logs leave the VM at once (§14.4). Response: Sev1, kill switch step 6 (§14.4): Iridium rotates the secret, the VM is rebuilt, the age identity, database passwords and link token are rotated, and `K_mask` is rotated per §13.2 if memory or the vault could have been read |
| **Compromised trusted machine** (malware, a malicious dependency of the offline tool, an AI agent running as the CTO's OS user) | Whatever the CTO's OS user can do | Forged tokens, plans and inventory signatures (still inside the hard blocks, which are code); the SITEST secret and the Keeper session; the raw ST-03 sample | §13.4: one named device, no AI agent under the user that holds Keeper and SSH, a minimal offline tool in its own venv, hardware keys for token and plan signing (§17 #27), a local mint and signing log checked against the first use of each new `jti` |
| **The CTO** (trusted, part-time, fallible) | Everything | Pasting the credential into a session; approving a broad plan; running parallel manual calls that collide with the masker; leaving agents on during a certification run | Credential only in the CTO's Keeper and the sops-encrypted file on the VM (§13.1); plan format with expiry and signed inventory (§8); the masker holds at most one of the two slots (§10); automatic pause during the CTO's dry runs and the certification run (§9) |
| **Someone with access to the hosting provider or the VM** (a stolen provider login, a provider employee, another admin of a shared provider team, the future deputy) | Open the provider console, snapshot or rebuild the VM, read its disk | Reading the secret, the vault or recordings from a disk image or a backup; changing the firewall | Provider account with only the CTO and hardware-key 2FA (§17 #23); provider guest agents removed, so the provider console cannot open a live root session (§14.1); secrets and keys encrypted at rest with sops and age, with the unlock key off the VM's disk and in memory only during unlock (recommended, §17 #22); vault values encrypted with the vault key (§6.3); backups encrypted to a key held in Keeper and an offline escrow (§13.2, §14.3); token and plan signing keys never on the VM (§13.2); SSH login alarm from the host (§14.4); Legal covers the provider's DPA and data location (§17 #24) |

## 3. Architecture

### 3.1 Where it runs

The masker runs on **one VM at a low-cost cloud provider**, not in AWS (CTO decision, 20 Oct 2026). DigitalOcean is the reference: Globalsat's Hub already runs on one DigitalOcean droplet with Docker Compose. Hetzner Cloud is the alternative. The design stays provider-neutral where that costs nothing: plain Linux, Docker Compose, a host firewall and the provider's cloud firewall. Only the provisioning outline (§14.3) names provider resources.

This departs from re-plan §3.4, which put the masker in Globalsat's AWS account next to the gateway. The change covers S2 and SITEST only. The production gateway (S4) stays in AWS, and its hosting details are decided in S4. The masker never moves into the production gateway's account, and it never shares a host, a database or a database role with anything that holds a production credential (§17 #14). It does not share the Hub droplet either. Region: the provider region with the best measured round trip to SITEST (§15.2 step 2). ST-15, the latency probe for the production gateway's AWS region, goes back to S3 and no longer gates the masker.

Docker Compose runs one container per role, so that only the signer ever holds the SITEST secret:

| Container | Docker networks | Holds | Network reach |
|---|---|---|---|
| `caddy` | `edge` (publishes 443), `front` (internal) | TLS certificate and key | Inbound 443. No direct egress: only the ACME certificate authority through the host egress proxy, if certificates are automatic (§3.2, §17 #11) |
| `masker` | `front`, `link`, `db` (all internal) | `K_mask` and the other masking keys, its database password, the link token; the token and plan public keys are baked into its image | **None outside the VM.** It talks to `caddy`, `signer` and `postgres` only |
| `signer` | `link`, `db` (internal), `sitest` (egress bridge) | The SITEST secret (§13.1), the inventory key, its database password, the link token; the plan public key is baked into its image | TCP 8443 to the pinned SITEST address only (§3.2). Its HTTP service listens only on its `link` address and refuses any caller without the link token |
| `postgres` | `db` | Data volume: call log, masked exchanges, vault, test inventory, plans, flags and windows, admin log, alarm events, permit ledger | None |
| `backup`, `alerter` (scheduled or long-running helpers) | `db`, plus one egress bridge each | `backup`: its read-only database role, the backup public key and the object-storage key. `alerter`: its database role (alarm events and admin log only), the alert token and the heartbeat URL | Only the host egress proxy, which lets `backup` reach the object-storage endpoint and `alerter` the alert endpoint and the heartbeat service (§3.2, §14.3, §14.4) |
| `retention` (one-off, daily timer) | `db` | Its database password | None |
| `admin` (one-off, run by the CTO over SSH) | `db` | Only while it runs, decrypted on demand: the admin database password, and for `inventory add` and `plan show` also `K_mask`, the vault key and the inventory key (§13.2) | None |

The signer is reachable only from the masker. `link` holds only those two containers, the signer's HTTP service binds only to its `link` address, and the masker sends the link token (§13.2) on every call, which the signer checks before anything else. `db` lets each container reach Postgres with its own role; nothing on `db` can reach the signer, so a compromised helper image (the `pg_dump` client, the upload client, the alert client) cannot pull unmasked SITEST data through it.

### 3.2 Network path to SITEST (egress only)

- Only the signer has a direct route off the VM, on its own Docker bridge network with a fixed subnet. Caddy, backup and alerter each have one narrow egress, through the host egress proxy only, to their own allowlisted names. The masker, Postgres and the retention and admin jobs sit only on internal Docker networks, which have no route off the VM. So a compromised masker process cannot open any outbound connection: no IP literal on 443, no DNS over HTTPS to a public resolver, no object storage, no DNS forwarding (below) (red-team case §11.5 #17).
- The SITEST endpoints are `iwstraining.iridium.com:8443`, paths `/iws-current/iws` (provisioning) and `/iwsReport-current/iws-report` (reporting) (catalog Rules; Annex D §1). Annex D's diagram also says "8843 to be confirmed"; the catalog says 8443. The firewalls open 8443 only.
- **Two firewalls, independent at the provider edge for 8443 only.** The host firewall (nftables) allows the signer's subnet TCP 8443 to the pinned SITEST address only, lets the helpers and Caddy reach only the egress proxy, and drops and logs everything else from every container. Its rules live in their own nftables table, not in Docker's chains, so Docker restarts and reloads of the rule set do not undo each other (§14.3), and a test checks them from inside each container (§15.1). The provider cloud firewall repeats the outbound rules at the provider edge: 8443 to the SITEST address, 53 to the provider's resolvers, 123 and 4460 to the NTS time servers, and 443. On 443 only the host restricts egress, and root on the host can remove that.
- **Host egress on 443 goes through one proxy.** Package mirrors, object storage, the ACME certificate authority and the alert services sit behind CDNs or shared addresses, so no firewall can pin them by address. A host egress proxy with a domain allowlist (mandatory; about 1 CTO-hour, *Inferred*, in §16.1) is the only process the host firewall lets out on 443. apt, hostwatch, the backup and alerter helpers and, for automatic certificates, Caddy go through it, each to its own allowlisted names, and it refuses any other name before resolving it. Images never come from a registry: the CTO moves every image, Caddy and Postgres included, from the trusted machine (§14.3). Where the provider's apt mirror and the object-storage endpoint have stable addresses, the cloud firewall's 443 rule is pinned to them (to verify).
- **Pinned address and no working DNS in the containers.** The signer connects to the reviewed SITEST address and checks the certificate for `iwstraining.iridium.com` (§13.3). Docker gives every container on a user-defined network its embedded resolver (127.0.0.11), so the design does not rely on its absence. It requires Docker Engine 26.0 or later (or 25.0.4 or 23.0.11), which stopped forwarding queries from internal networks (CVE-2024-29018), and Compose gives every container an unroutable upstream (`dns: [192.0.2.53]`), which nftables drops, so Docker forwards from the container's namespace, where the drop applies (to verify on the chosen version). The helpers and Caddy need no resolver, because the proxy resolves their allowlisted names. The startup self-test checks that no name resolves (§13.3). The host's own outbound 53 goes only to the provider's resolvers.
- **Static IP.** The VM has a static public IPv4, which Iridium may later be asked to allowlist (re-plan §8.2). On DigitalOcean a droplet's own public IPv4 stays fixed for the droplet's life. A Reserved IP survives a rebuild, but outbound traffic leaves from it only after a routing change (to verify). On Hetzner a Primary IP is assigned to the server directly. IPv6 is disabled on the VM and in Docker, so no rule needs an IPv6 twin (§14.3).
- **Time.** chrony uses NTS-authenticated servers (for example `time.cloudflare.com` and `nts.netnod.se`; NTS-KE on TCP 4460) with `makestep` and `maxchange` limits, because token expiry, plan validity, pause windows and IWS timestamps all depend on the clock, and plain NTP can be shifted by anyone on the path. The signer compares each IWS response's `Date` header with its own clock and raises a clock-skew alarm above 5 s (*Inferred*). IWS signatures carry a UTC timestamp, and the skew IWS tolerates is unknown (Annex D open questions).

### 3.3 How agents in a cloud coding session reach it

The agent session runs in Anthropic's cloud. Its egress goes through an agent proxy with a domain allowlist, and its source IPs are not Globalsat's to know or pin. So network location cannot authenticate it; a credential must.

| Option | How it works | For | Against |
|---|---|---|---|
| **A. HTTPS endpoint + CTO-minted session tokens** (accepted, §17 #1) | Caddy on the VM terminates TLS on a Globalsat subdomain. Each request carries a short-lived token signed by a key only the CTO holds (off the VM, used only on the CTO's trusted machine, §13.4). The masker verifies it before any other work | Simple for agents (one header). No cloud credential in the session. Scoped (read scopes, plus one plan for writes). Short-lived and revocable. Works with any agent proxy | A public endpoint exists; it must reject unauthenticated traffic cheaply. The token is a bearer credential the agent holds, and it is visible to the agent proxy layer, which terminates TLS |
| B. Mutual TLS | The reverse proxy verifies a client certificate | Binds the client to a key | Likely infeasible: the agent proxy terminates TLS, so the client certificate cannot reach the VM. The client key is still a bearer secret in the session. Longer-lived; revocation and rotation are harder. More setup for one person |
| C. Tunnel (a VPN, an SSH tunnel or a tunnel service) | The session opens a tunnel to the VM | No public endpoint | Needs tunnel software and more allowed hosts in the session. Long-lived tunnel credentials. A tunnel onto the VM widens what a compromised session can reach |
| D. Private overlay (Tailscale or WireGuard) from the session | The session joins the overlay and reaches the masker on a private address | No public endpoint | Puts a long-lived node key in the agent session; the agent proxy may not carry overlay traffic at all (to verify). Overlay membership is broader than one API |

**Decision: A.** Details:

- **Token.** A compact JWS signed ES256 with the token-signing key (ECDSA P-256). The CTO generates that key on the trusted machine, on a hardware key (recommended, §17 #27) or in Keeper. It never reaches the VM. The public key is baked into the masker image, so changing it is a reviewed rebuild, not a file edit on the host (§13.2). The masker accepts only ES256 with the pinned key id, and ignores `jku`, `x5u` and `jwk` headers. Tokens carry a fixed prefix (`gsm_`) so gitleaks and GitHub secret scanning can find them (§11.3). Claims: `sub` (the label of the cloud environment), `scope` (`read:catalog`, `read:inventory` or `read:sp`, plus `write:<plan-id>` for writes; §4.2, §17 #19), `iat`, `exp` (§17 #12), `jti`, and rate tier. On every request the masker checks signature, expiry, scope and the revocation list (`jti` denylist and a global "not before" time, read from the database), and fails closed if that read fails. It logs the source IP per `jti`.
- **Minting.** The CTO runs `masker_offline mint` on the trusted machine (§13.4), with the signing key on the hardware key or read from Keeper and never written to disk. Each mint is appended to a local log. Minting needs no connection to the VM. It never runs in an agent session.
- **Delivery to the session.** Cloud-environment secrets and variables apply to the whole environment: every new session in it picks them up. So agents use a **dedicated cloud environment for SITEST work**, and `sub` names that environment. The CTO sets the token there, preferably as a Network secret bound to the masker host, if that injects the header at the proxy without exposing the value to the session (to verify); otherwise as the environment variable `MASKER_TOKEN`. Never in chat, a document, git or a log. The platform `CLAUDE.md` forbids agents to hold credentials, so §12.3 adds this token to it as the one exception.
- **Unauthenticated traffic.** Rejected with a bare 401 before any parsing; only the health check `/healthz` is exempt and returns 200 with no body. Per-source connection and request-rate limits in the host firewall and in Caddy cap abuse, with limits loose enough for the agent proxy's shared source addresses (*Inferred*; §14.3). Caddy needs a third-party module for request-rate limits, which means a custom build with its own `Dockerfile.caddy` and licence review (§14.3); nginx has `limit_req` built in and is the alternative. The masker counts token failures per minute instead of logging each one, and Caddy's access log is sampled, so a flood cannot rotate the journal (§9).
- **Agent environment network allowlist.** The dedicated environment must allow the masker's host name on 443 (for example `masker.<globalsat-domain>` [FILL: subdomain]; open decision §17 #11) and only the package-manager hosts its setup needs; whether the allowlist can be narrowed further after setup is to be checked in the environment settings. It must **not** allow `*.iridium.com`, including the WSDL Explorer host, so a session has no direct path to IWS even by mistake. Only the CTO changes the environment's network settings.

## 4. Agent interface

### 4.1 Request and response shapes

The masker speaks the same shape as the gateway's internal interface (Annex D §2.1; Annex F §6.2): a SOAP 1.2 envelope whose `<request>` carries no authentication fields, plus headers. Agents can then point the clients they build at the masker now and at the gateway later.

**Request.** `POST /iws/sitest/{provisioning|reporting}` with:

| Part | Content |
|---|---|
| `Authorization` | `Bearer <session token>` |
| Body | SOAP 1.2 envelope; the body's root element is the operation (exact WSDL case); `<request>` without `iwsUsername`, `signature`, `timestamp`, `serviceProviderAccountNumber`, `caller` or `callerPassword`. Validated against the WSDL schema before any policy check (§7). Identifiers are surrogates (§6). Maximum 256 KB (*Inferred*) |
| `X-SP` | Optional SP constant (`SP-0001`…, §6.2); the masker maps it to one of Globalsat's SP account numbers, since Globalsat may have several (Annex D §2.9); the signer gives it those numbers and `iwsUsername` at start, never the secret key (§12.1). Absent: the default SP |
| `X-Correlation-Id` | Agent's own id, limited to `[A-Za-z0-9-]{1,64}`, echoed back |
| `X-Deadline` | Optional; capped by the method's timeout |
| `X-Test-Plan` | Required for writes (§8) |
| `X-Idempotency-Key` | Required for writes (§8) |
| `X-Dry-Run` | `true` validates and shows the final masked request without sending (§8) |

**Response.** The masked SOAP response or fault, element for element, so agents see the real shape (`xsi:type`, nil versus absent, empty success). Headers: `X-Masker-Call-Id`, `X-Masker-Decision` (`sent`, `dry-run`, `refused`, `blocked`, `busy`, `unknown`), `X-Masker-Permit-Wait` (bucketed: `0`, `<1s`, `<10s`, so it does not reveal when others use IWS), `X-Masker-Iws-Ms`, `X-Masker-Dropped` (count of elements the policy removed), and `Cache-Control: no-store` on every response. No IWS HTTP header or cookie is forwarded.

**Refusals** come back as a SOAP fault whose detail holds a masker element, never an IWS one, with an HTTP status: `401` bad token; `403` method not allowed, always refused, plan missing or not covering the request, identifier not issued; `409` idempotency conflict; `413` too large; `422` request failed schema validation or policy (for example a real-looking identifier in a free-text field); `429` rate limit or budget spent; `503` with `Retry-After` for `IWS_BUSY` (Annex D §2.4); `502` masking blocked by the runtime detector or any masking-stage failure (§11.4). `IDENTIFIER_NOT_ISSUED` also covers an issued surrogate outside the token's read scope, by the same code path and before any IWS call, so the answer does not reveal which surrogates exist. Each refusal has a stable code, such as `ALWAYS_REFUSED_DEACTIVE`, `ALWAYS_REFUSED_BULK`, `METHOD_NOT_ALLOWED`, `PLAN_REQUIRED`, `IDENTIFIER_NOT_ISSUED`, `MASKING_BLOCKED`.

**Small JSON endpoints:** `GET /v1/session` (scope, expiry, remaining budgets), `GET /v1/methods` (the allowlist with class, endpoint and limits), `GET /v1/calls/{id}` (the caller's own call-log row, without the request hash; ownership is checked against the token's `jti`, and call ids are random UUIDv4). Masked exchanges are not readable through the masker: its database role can only insert them (§9). There is no endpoint that resolves a surrogate to a real value.

Example (fake values): the agent sends `getSubscriberAccount` with `<accountNo>SUB-9004217</accountNo>`. The masker resolves the surrogate in the vault, sends the real account number to SITEST, and returns the account with `imei` `990000000318651`, `sim` deviceNumber `9900000007582043714`, `msisdn` `990000058306`, and `createdBy` `user-k3f9q2m7`. Each type is derived independently, so the surrogates of one account share no digits (§6.3).

## 6. Masking scheme

### 6.1 Treatments

| Code | Treatment | Reversible by the masker | Used for |
|---|---|---|---|
| T-NUM | Keyed tokenization into a digit surrogate of the same length (a fixed length for number types of unknown format, §6.2), in a reserved prefix, with a valid check digit where the type has one | Yes, through the vault | IMEI, ICCID, IMSI, MSISDN family, capcode, `SUB-`/`SC-` numbers, IMO, MMSI, 19-digit serials, numeric-typed IDs |
| T-STR | Keyed tokenization into a labeled string, `<Label>-<8 base32 chars>`. On an element with a numeric XSD type it becomes T-NUM | Yes | Vessel, organization and group names, `spReference`, customer-entered descriptions, VPN names, other IDs |
| T-IP | Keyed tokenization into a reserved address range | Yes | IPv4, IPv6, subnets |
| T-HOST / T-EMAIL | Keyed tokenization under the reserved domain `example.invalid`; `*` wildcards and ports kept | Yes | Delivery hosts, filter domains, emails |
| P-ONE | One-way pseudonym with the same derivation, no vault row | No | Person names, logins, contact phones, postal address parts, called and calling numbers |
| C | Constant per distinct real value | No | SP account numbers and names, `iwsUsername` |
| G | Generalize | No | Coordinates (1 degree); later, if allowed, vessel build year (decade), tonnage and capacity (bands) |
| D | Drop: on a string element the value is replaced by `REDACTED` and the element kept, so the shape stays; other types follow the XSD rule below | No | Secrets, PINs, PUKs, download URLs, LAC, altitude, vessel quasi-identifiers |
| F | Free text: replaced as a whole by `Text-<8>` (P-ONE derivation, no vault row) unless the value fully matches a reviewed message template, whose typed slots are masked by type (§6.4) | No | Error messages, fault text, reasons, system and catalog descriptions |
| N | Parse the embedded XML or CSV and mask it with the same rules; drop it if it does not parse | — | IWS log and queue payloads, inline report rows |

**Every output must be valid for the element's XSD type** in the field map, so agents' bindings and strict validation keep working. D on a numeric or date element writes `xsi:nil` if the element is nillable; otherwise it removes the element if `minOccurs` is 0; otherwise it writes a type-valid sentinel listed in `overrides.yaml`. T-STR on a numeric type becomes T-NUM. G keeps the type.

Values are kept only where the field map says keep (§6.5): dates, statuses, enums, plan and bundle IDs, catalog names, counts, flags.

### 6.2 Surrogate formats

The reserved prefixes are tentative. Each must occur in **zero** real values of its type in SITEST. Only the masker sees real values, so it checks this itself: when issuing a surrogate, it counts real values that fall inside the type's reserved prefix, refuses to issue for them and writes an incident (count only, never the value). The first recording session (§15.2) reads this counter, and so does every detected SITEST refresh (§8.2). If a prefix does occur, the masker uses the next candidate, and the change is a reviewed constant.

| Type | Real format | Surrogate format | Fake example |
|---|---|---|---|
| IMEI | 15 digits; SBD/M2M+ start with 3 and end with 0 [OW]; no check digit assumed | `99` + 12 derived digits + Luhn digit | `990000000318651` |
| ICCID | 19 digits | `99` + 16 derived digits + Luhn digit | `9900000007582043714` |
| IMSI | 15 digits | `99` + 13 derived digits | `990000000593607` |
| MSISDN | 12 digits starting 8816/8817 [OW] | `99` + 10 derived digits | `990000058306` |
| Other numbers (MSISDN-B/C, PLUS1/PLUS7, local, follow-me, ISDN-A) | Unknown or variable length | Fixed 12 digits, `99` + 10 derived digits, whatever the real length, so the length does not reveal the country | `990000271940` |
| Contract | `SUB-` + 7 digits | `SUB-9` + 6 derived digits (fallback `SUB-X` + 6 digits) | `SUB-9004217` |
| Voucher account | `SC-` prefix; length undocumented (uncertain) | `SC-99` + derived digits, same length | `SC-990815` |
| IPv4 | | `240.0.0.0/4` (reserved, never routable) | `240.18.7.33` |
| IPv6 | | `2001:db8::/32` (documentation range) | `2001:db8::9c1e` |
| Host | | `h-<8>.example.invalid` | `h-k3f9q2m7.example.invalid:4000` |
| Email | | `u-<8>@example.invalid` | `u-k3f9q2m7@example.invalid` |
| Names | | `Name-<8>`, `Vessel-<8>`, `Org-<8>`, `Group-<8>`, `user-<8>` | `Vessel-p2x8c4ra` |
| IMO, MMSI | 7 and 9 digits | `99` + derived digits, same length; IMO check digit recomputed (*Inferred*) | `9900588` |
| SP | | `SP-0001`, `SP-Name-0001` | |

Why these shapes: the same length (where the real length is fixed) and digits keep agent code, XSD types and lengths working; the reserved prefix makes every surrogate **recognizably non-real**. Real values can start with `99` too (for example 12-digit numbers under the assigned E.164 codes 992–996 and 998; general knowledge), so the leak detector exempts only surrogates the masker itself placed in the response, never a value just because of its prefix (§11.1). Domains and address ranges are reserved by standards (`example.invalid`, `240.0.0.0/4`, `2001:db8::/32`; general knowledge, not from the sources). Surrogates that break IWS's own format rules (for example an MSISDN that does not start 8816/8817) are fine: IWS only ever sees real values. Agent tests of format validation use synthetic data, not surrogates.

### 6.3 Derivation, consistency, collisions and check digits

- **Derivation.** `h = HMAC-SHA256(K_mask, TLV(type) || TLV(version) || TLV(real_value) || TLV(counter))`, where each field is length-prefixed, so distinct inputs never concatenate to the same string. The digits or base32 characters of the surrogate body come from `h` (digits: `h` as an integer modulo `10^n`). `type` keeps an IMEI and an IMSI with the same digits apart, and every type is derived independently. `counter` starts at 0.
- **Consistency.** The derivation is deterministic, so the same real value gets the same surrogate in every call, every session and across masker restarts. Consistency is global, not per session. Fixtures do not depend on it: they are re-pseudonymized on export (§9). After a SITEST refresh, values that survive keep their surrogates, but write scope is reset (§8.2).
- **Vault.** Every reversible surrogate issued has a row: `(type, surrogate, counter) → AES-256-GCM(real_value)`, plus first-seen and last-seen times. The vault is the record of what the masker issued (§7). Expired rows become tombstones whose slot is never reused (§9).
- **Collisions.** On issue, the masker looks up `(type, surrogate)`. If the row (or a tombstone) holds a different value, it increments `counter` and derives again. Collisions are expected, not rare. Surrogate space per type (*Inferred*): `SUB-` 10^6 (about 500 expected collisions at the assumed ~32,000 contracts, Annex D §2.4); IMO 10^4; `SC-` 10^(digits − 2); MMSI 10^7; MSISDN and other numbers 10^10; IMEI 10^12; IMSI 10^13; ICCID 10^16. The masker refuses to issue past 50% occupancy of a type's space (tombstones count) and raises an alarm (*Inferred* threshold); for IMO and short `SC-` numbers that cap is reachable, and the CTO then approves a longer or second prefix.
- **Check digits.** Recomputed for the surrogate (Luhn for IMEI and ICCID). The real value's check digit is never copied.
- **Key.** `K_mask` is a 256-bit random key the CTO generates once on the trusted machine (`masker_offline keys init`). Keeper holds the custody copy, with an offline escrow (§13.2). On the VM it is a root-only sops file, decrypted into a tmpfs file mounted into the masker container (and into the one-off admin container while `inventory add` or `plan show` runs), never into an image, an environment variable or a log (§13.2). It is never rotated in normal operation, because rotation changes every surrogate. Surrogate epochs are not in S2 (§17 #20).

### 6.4 Free text, embedded payloads and faults

- **Known-value replacement.** For each call, the masker keeps the set of real values it replaced in structured fields, the real values it put into the request (§7), and the auth values injected for the call (`iwsUsername`, `serviceProviderAccountNumber` and the signed timestamp, which the signer passes to the masker; the signature never leaves the signer, which redacts any echo of it before returning the response, §12.1). It then replaces any occurrence of those strings in free text, fault text and embedded payloads with the matching surrogate, constant or `REDACTED`. This catches IWS error messages that echo the request value.
- **Cross-call known values.** The masker keeps a keyed-hash set (HMAC with its own key, held like `K_mask` (§13.2), no plain values; stored and expired with the vault) of every real T-STR, P-ONE and T-EMAIL value of 4 or more characters ever seen in a structured field. Word sequences (1–4 words) in output strings are checked against it: a hit is tokenized in F fields and blocks the response in kept fields. This is the backstop for names, which match no pattern.
- **Free text (F).** A value is kept only if it fully matches a reviewed message template, for example an IWS error message with a typed slot for an account number. Templates are added by the CTO from recorded masked samples, never copied from the catalog. Template slots are masked by their type. Anything else is replaced as a whole by `Text-<8>`. `otherInfo`, tracker and email bodies, and `reason` are always tokenized.
- **Pattern detectors** (§11.1) then run over every template slot and every kept string. A match is tokenized by its detected type.
- **`spReference` and customer-entered descriptions** (account metadata, subscriber organization, vessel, resource group, tracker, pooling group, voucher order, PTT device) are tokenized as whole values (T-STR, reversible), because they may hold customer names or order numbers. Catalog and system descriptions (outages, call types, IMEI profiles, notifications) get F, so templates can keep the ones agents need.
- **Embedded XML** (`iwsLogImpl.request`/`response`, `baseQueueEntryImpl.request`/`response`) is unescaped, parsed with the same safe parser, masked with the field map of the operation it names, and re-escaped. It is masked only if its root element equals `requestedOperation` (or `operation`) and that operation is allowlisted; otherwise, or if it does not parse, the element is dropped (D). Auth fields inside it (`signature`, `callerPassword`) are dropped first.
- **CSV rows** (`reportResultDetailsEntryImpl.row`) need the report's column map (§17 #6). Until then the method is refused.

### 6.5 Unknown elements: fail closed

Every element and attribute path in every allowed method's request and response, keyed by (operation, `xsi:type`, path), is classified in a field map: one of the treatments above, or "keep". The generator reads the live WSDL (§12.2) and emits every path as **UNCLASSIFIED**. Only the reviewed override file assigns a treatment, `keep` included. The generator may propose `keep` for booleans, enumerations, dates and numeric quantities; each proposal is listed in the generated file for review and takes effect only once copied into the override file. It never proposes `keep` for `xsd:string` or ID-like integers: the CTO classifies those one by one (for example catalog names and plan IDs). CI fails on any UNCLASSIFIED path in an allowed method.

At runtime, an unknown path, an unknown `xsi:type`, any attribute other than `xsi:type` and `xsi:nil`, or non-whitespace text outside a leaf element blocks the whole response (§11.4) until the CTO classifies it; the metric raises an alarm. `X-Masker-Dropped` counts the elements the policy removes on purpose. Strict mode is a code constant: there is no non-strict mode in S2. This mirrors the gateway rule that CI fails on an unclassified WSDL operation (Annex D §2.1).

### 6.6 Decision: keyed tokenization with a vault, not FF1

| | Keyed tokenization + vault (decided, §17 #3) | NIST FF1 format-preserving encryption with a protected key |
|---|---|---|
| Consistency | Deterministic derivation | Deterministic |
| Reverse mapping | Vault lookup | Decryption, no storage |
| Scope limit (§7) | Natural: only issued surrogates have a vault row, so a guessed surrogate maps to nothing | None: every string in the format decrypts to some real value, so an agent could enumerate surrogates and act on arbitrary real lines; scope needs a separate allowlist anyway |
| Recognizably non-real | Yes: room for a reserved prefix, because the vault, not the format, carries the information | Hard: a reversible mapping of n-digit strings onto n digits leaves no room for a reserved prefix plus a valid check digit |
| Leak detection | At runtime: any real-format value the masker did not place in this response. Offline (fixture scans, people reading output): anything outside the reserved prefixes | Offline scans and readers cannot tell a surrogate from a real value by format |
| Storage and state | A vault table (rows grow with the identifiers seen) | None |
| Library risk | HMAC and AES-GCM from the standard library and `cryptography` | Few maintained, audited Python FF1 implementations (*Inferred*; would need its own review) |

The vault costs a table and one lookup per identifier. Recognizable surrogates and the scope limit are worth that.

## 7. Requests that carry masked identifiers

1. The masker validates the request against the WSDL schema, then classifies every element with the field map (§6.5). Any element beyond its `maxOccurs`, mixed content, a comment, processing instruction, CDATA section or DTD, an unknown attribute, or an `xsi:type` outside the field map refuses the request with `422`. An unknown element refuses it too. This closes parser differentials: the masker reads the first of two duplicate elements, while a Java binding on the IWS side may keep the last.
2. For each identifier field, the value must be a surrogate **the masker issued**: a vault row for `(type, surrogate)` must exist. The type comes from the field map or the typing enum (§5.2). If no row exists, or the surrogate is outside the token's read scope (§4.2), the request is refused with `IDENTIFIER_NOT_ISSUED`, by the same code path. A real-format value outside the reserved prefixes is refused with `422`, because no agent should hold one.
3. The masker replaces each surrogate with the decrypted real value in memory and records the pair for known-value replacement on the way back (§6.4).
4. Free-text fields in the request are scanned by the detectors. A match refuses the request: this stops an agent from writing a real identifier into SITEST, from where it could come back unmasked in another field.
5. **Reads.** Surrogates are global handles: any issued surrogate can be used for reads within the token's read scope. Fixtures carry re-pseudonymized values that resolve to nothing (§9). Guessing works rarely (about 3% of guessed `SUB-` surrogates hit an issued row at 32,000 issued, *Inferred*), so guesses alarm (§11.5 #6) and daily budgets cap what any token can pull (§10).
6. **Writes** may use only surrogates that are both issued **and** in the plan's scope: the plan's signed test inventory, or accounts derived from it (§8.2).
7. Literal values a write needs must be real, non-personal values Globalsat controls (for example `spReference` `GS:TEST-001`) and must be listed in the plan's `allowed_literals`. The CTO's test mailbox is registered inventory of type EMAIL, not a literal. Anything else that looks like an identifier is refused.
8. **Search inputs.** Every search input aimed at a masked field is identifier-typed and must be an exact issued surrogate; free text is never accepted in a search input, so partial-match searches cannot be used to rebuild a real name character by character. Surrogates in wildcards (`*`, `%`) cannot be mapped, so wildcards on identifier filters are refused. `accountSearch.filterCond` must be `EQUALS` (absent means `EQUALS`): `CONTAINS`, `LIKE`, `NOT_EQUAL` and the other negations are refused. `getVessels` accepts only `id`, `imo`, `mmsi` or a full issued `Vessel-` surrogate. `getSubscriberOrganizations` accepts only an issued `Id`. `getQueueEntries.createdBy` is overwritten with the masker's own value for the session (its `caller` or the IWS username, whichever IWS records; uncertain until the recording session), so no agent types a real login.

## 8. Write guard (S2b)

### 8.1 Test plan format

A plan is a YAML file in this repository under `test-plans/` (§17 #15), reviewed in a PR like code, then signed by the CTO and loaded into the masker in the two halves below. The CTO reviews raw YAML but signs what the loader parses, so the two must not differ:

- Plans are parsed with a strict loader: no duplicate keys, anchors, aliases, merge keys or tags; schema-validated; unknown keys refused.
- Loading runs in two halves, because the plan-approval key never reaches the VM. On the VM, `masker-admin plan show` (in the one-off admin container, over SSH) takes the merged file the CTO copies from `main` with its commit SHA and blob hash, checks the hash, and prints the canonical parsed plan (with each inventory entry's service and the last 4 digits of its real value, to compare with Iridium's assignment list) and its digest. On the trusted machine, `masker_offline plan sign` (§13.4) parses the same commit from its own clone with the same strict loader (`common/plan_format.py`), refuses unless its digest matches the VM's, and signs only after the CTO types the plan id. `plan attach` stores the signature on the VM. The commit SHA and the plan signature are recorded in the masker database; neither is committed, because a file cannot contain the SHA of the commit that merges it.

```yaml
id: TP-2026-001
title: SBD activation, suspend and resume on assigned test inventory
purpose: Annex F ST-04, checklist v1.7 "Account Activation - SBD"
valid_from: 2026-11-23T00:00:00Z
expires_at: 2026-11-30T00:00:00Z          # at most 14 days after valid_from
max_writes: 20                            # budget for the whole plan
allowed_methods:
  - method: activateSubscriber
    service_types: [SBD]
  - method: setSubscriberAccountStatus
    new_status: [SUSPENDED, ACTIVE]      # DEACTIVE and CLOSED are hard-blocked anyway
  - method: accountUpdate
    status_change: forbidden
    mutable_fields: [subscriberAccountMetadata.spReference]   # every other difference is refused (§8.2 step 6)
allowed_inventory:                        # surrogates of signed test-inventory rows only
  - {type: IMEI, surrogate: "990000000725905", service: SBD}
  - {type: IMEI, surrogate: "990000000182073", service: SBD}
  - {type: EMAIL, surrogate: "u-q7m2x9k4@example.invalid", service: SBD}   # the CTO's test mailbox, registered inventory
allowed_literals:                         # real, non-personal values Globalsat controls
  - {field: subscriberAccountMetadata.spReference, value: "GS:TEST-001"}
dry_run_required: true                    # each request hash must be dry-run before it is sent
# The commit SHA and the plan signature are recorded in the masker database at load, never in this file.
```

**Test inventory registration.** Iridium's assigned test inventory (re-plan §11.1 Q10) is registered by the CTO with `masker-admin inventory add`, run over SSH in the one-off admin container (§14.3, §17 #16). The CTO types each value interactively, never as a command-line argument, which shell history or a process listing could keep. The tool writes the real value to the vault and a **pending** row to a separate **test-inventory table**, holding the HMAC of the real value under the inventory key (§13.2), and prints only the surrogate for the plan. Only the admin database role can write that table; the masker's and the signer's roles have `SELECT` only, and the admin role's password and the keys `inventory add` needs are decrypted into the admin container only while it runs. A pending row is unusable until `masker_offline inventory sign` on the trusted machine shows it (type, surrogate, service, HMAC). The CTO types the real value again there, from Iridium's assignment list; the tool computes its HMAC with the inventory key and signs with the plan-approval key over (type, surrogate, HMAC, service) only if the two HMACs are equal. So a tampered admin tool cannot get a real customer line signed under a test surrogate. `plan show` and `plan sign` refuse any `allowed_inventory` entry that is not a signed inventory row, and the signer checks every write against the signed rows itself (§12.1). The offline signatures, the signer's write guard and the database grants are the control, not the CLI's own checks (§12.2). Neither the masker container nor the database can forge an approval. Root on the host bypasses every check on the VM and is handled as a Sev1 (§2.2, §14.4). Real inventory values never enter git, a plan file or an agent session.

### 8.2 Enforcement, in order

1. Token scope includes `write:<plan-id>` and matches `X-Test-Plan`.
2. The plan exists, its signature verifies against the plan-approval public key baked into the image, the current time is inside its validity, it is not revoked, and its write budget is not spent. Agents cannot sign plans: the private key exists only on the CTO's hardware key or in Keeper, and is used only on the trusted machine.
3. The method is in the global write allowlist (§4.2) **and** in the plan, with its constraints (service type, allowed status values).
4. The hard blocks pass (§8.5).
5. Every identifier is issued **and** in scope (§7): a signed test-inventory row named in `allowed_inventory` (the signature is re-verified on every write), or a derived account of this plan. Derived accounts come only from the success field of an `activateSubscriber` response, after a read confirms that the account's device is the plan's signed test-inventory device. Writes address accounts by contract number only (`updateType` `SUBSCRIBER_ACCOUNT_NUMBER`, or `accountNo`). Before every write, the masker re-reads the target and refuses unless its devices are signed test inventory, because SITEST is refreshed from production and a number in scope yesterday can belong to a real contract today. Derived sets expire with the plan and are cleared on a detected SITEST refresh (a `getProjectVersion` or `getSystemStatus` version change, or a CTO flag); writes then stay off until the CTO re-enables them.
6. `accountUpdate`: the masker reads the current account (`getSubscriberAccount`, required before `accountUpdate` anyway; Annex D D4) and diffs the agent's object against that read. Fields with non-reversible treatments (P-ONE, C, G, D, F) must equal the masked value from the read and are restored to the real values from the read. Each changed field must be listed in the plan's `mutable_fields` for that method; any other difference is refused. `accountStatus` always comes from the read, and `sim`, `imei`, `msisdn` and `ip` may not change in S2b (§4.3).
7. If the plan requires it, a dry run with the same request hash was made in this plan within the last 24 h.
8. Idempotency (§8.4), then the permit, then the send. No automatic retry on a write (Annex D §2.5). Before it takes the permit, the signer repeats the plan, inventory, budget and flag checks on the final bytes (§12.1).

### 8.3 Dry run

`X-Dry-Run: true` runs steps 1–7 and the unmasking, builds the final request without signing it, and returns the **masked** final request plus the verdict, without contacting IWS. The record stores the request hash, so step 7 can match it. A dry run never spends write budget.

**Request hash** = HMAC-SHA256(`K_req`, canonical masked request). The canonical form is the agent's surrogate-bearing request after schema validation, without headers or timestamps, so a dry run and its send match. `K_req` is a separate key, held like `K_mask` (§13.2). The hash is never returned to agents and is not part of `/v1/calls`. Nothing anywhere hashes unmasked bytes: a plain hash of a low-entropy real identifier could be reversed by brute force.

### 8.4 Idempotency

`X-Idempotency-Key` is required on writes. The masker stores `(plan, key) → request hash, call id, outcome, masked response`. The same key with the same hash returns the stored masked response without resending. The same key with a different hash is refused with `409`. A timeout or an IWS system error on a write is recorded as `unknown`, never retried; the agent resolves it with the probes in Annex D §2.5 (for example `accountSearch` after an activation), all of which are reads.

### 8.5 The hard block on DEACTIVE

The block is code, not plan data, so no plan can lift it:

- `setSubscriberAccountStatus` with `newStatus` `DEACTIVE` or `CLOSED`, or with `bypassQuarantine` present with any value other than `FALSE`, is refused with `ALWAYS_REFUSED_DEACTIVE` before any other check. The comparison runs after NFKC normalization, trimming and case folding, so ` DEACTIVE `, `Deactive` or full-width text are caught.
- `accountUpdate` that would change `accountStatus` is refused (step 6).
- `activateSubscriber` with `bulkAction` other than `FALSE` or absent, any `*BulkDetails` element, or a `BULK` literal in a device field is refused with `ALWAYS_REFUSED_BULK`.
- Every method in the always-refused list (§4.3) is refused, including bulk and destructive ones.
- The outgoing envelope is **rebuilt from scratch**, never edited from the agent's tree: no SOAP Header, exactly one Body child, enum values such as `newStatus` written from the masker's own constants (`SUSPENDED`, `ACTIVE`), never the agent's bytes; Content-Type and action set by the transport; no agent header forwarded. The check then runs again on the final bytes after unmasking and auth injection.
- The hard block applies to every token, the CTO's included.
- Any attempt raises an alarm (§14.4). It is never silent.
- The block and its tests live in files on the mandatory review list (`masker/policy/hard_blocks.py`, `tests/masker/test_mask_hard_blocks.py`).

DEACTIVE in the spike's SBD lifecycle and in the final dry run stays a CTO action outside the masker (re-plan §3.2; S5). The CTO's path (decided, §17 #7): a manual call from the CTO's trusted machine, with agents paused so that no agent request competes for the two permits, recorded afterwards with `masker-admin note` so the call log and the evidence index show it. Each DEACTIVE of an SBD line releases its IMEI (Annex E §1.4), which frees test inventory for the next ST-04 run.

## 9. Recorder and call log

**What is stored, masked only.** No unmasked request or response is ever written to disk, a log or a backup. Everything below lives in the Postgres container on the masker VM, on a provider block-storage volume (§14.3), and leaves the VM only in encrypted backups.

| Record | Fields | Where |
|---|---|---|
| Call log row (append-only: the masker's database role has no `UPDATE` or `DELETE` on this table) | `call_id` (UUIDv4), UTC start and end, token `jti` and `sub`, source IP, plan id, operation, endpoint, class (read or write), dry run, decision and refusal code, permit wait, IWS duration, outcome (`ok`, IWS fault code from `errorCodeEnum`, `unknown`), the `caller` value sent to IWS, the signed UTC timestamp sent, IWS request id if returned, idempotency key, request hash (keyed, §8.3), counts of dropped elements and detector hits | Postgres, schema `masker` |
| Masked exchange | Masked request and masked response XML, compressed. For refused requests, every detector hit in the stored body is replaced by `<detector-id>`, and the detectors run again before the insert | Postgres table `masker.exchanges` (compressed). The masker's database role has `INSERT` only: no `SELECT`, `UPDATE` or `DELETE`. A retention role can only call a function that deletes rows past retention (§14.3); the admin role reads rows for export; the backup role reads everything, for `pg_dump` only |
| Incident row (runtime detector) | `call_id`, element path, detector id; never the value | Postgres |
| Vault | §6.3, plus the cross-call known-value hash set (§6.4) | Postgres, schema `masker_vault`, separate role, values encrypted with the vault key (§13.2) |
| Test inventory | Signed rows (§8.1) | Postgres, schema `masker_inventory`; the admin role writes, the masker's and the signer's roles read |
| Admin log (append-only) | Every admin action: action code, target (surrogate, plan id or flag), time; never a real value | Postgres; the admin role has `INSERT` only; the alerter's role reads it (§14.4) |

**Application logging.** Logs are structured and carry an allowlisted field set only: call id, codes, timings, counts. A logging filter runs the §11.1 detectors and the known-value sets on every record; on a hit it drops the record and raises the leak alarm. Exceptions on the IWS path are logged as type and code only, with no message and no local variables, because lxml, aiohttp and validation errors can echo input. There is no debug mode. Validation errors return codes, not inputs. Metric dimensions never carry values. A leak test drives every error path with canary data and asserts that the logs stay clean (§11.2). Container logs go to the VM's journald through Docker's logging driver and stay on the VM: 90 days, size-capped (*Inferred*); token failures are counted per minute, not logged one by one, and Caddy's access log is sampled, so a flood from the internet cannot rotate the journal. Application logs are not shipped off the VM. Host security logs (auth, `sudo`, Docker events, nftables drops), which carry no personal data, are shipped in near real time to an append-only bucket, so an intruder cannot erase what was already sent (§14.4). Alarms leave the VM only as enumerated codes and bucketed counts through the alert channel (§14.4).

**Retention (working periods, §17 #8; Legal sets the final periods per country, re-plan §5 item 5).** Call log: 18 months, like the gateway's technical log (Annex D §2.8). Masked exchanges: 90 days, except samples promoted to fixtures. Encrypted backups: 30 days (*Inferred*), so a deleted vault value is gone from every copy within about 120 days. Vault rows: after 90 days unused, the encrypted value is deleted, but `(type, surrogate, counter)` stays reserved forever as a tombstone: a reserved slot is never issued to another value, so an old surrogate in a session or plan can never come to mean a different person. Test-inventory rows and rows referenced by a loaded plan never expire. Masked data is still pseudonymized personal data while the vault exists. Deterministic derivation means the next sighting of a value recreates its old surrogate, so deleting rows does not unlink anything (epochs are §17 #20). Agent transcripts are also pseudonymized personal data, held by the agent provider outside Globalsat's retention; Legal confirms the basis. The vault, which holds real identifiers (encrypted), the call log and the backups sit with the hosting provider (DigitalOcean by default) in the region chosen in §15.2 and in the backup region (§14.3), so Legal's data-protection task must cover that provider's DPA, sub-processors and data location (§17 #24).

**Fixtures.** The CTO promotes chosen masked exchanges to `tests/fixtures/masked/` with `masker-admin export`. Export re-pseudonymizes them with a separate one-way fixture key (no vault rows, consistent within the fixture set), so fixture values never resolve live, then re-runs every detector and the fixture scan (§11.3). They reach git only through a PR the CTO reviews; the path matches `**/*mask*` in CODEOWNERS. They feed the IWS simulator and contract tests (Annex E §5; re-plan §3.1).

**How the evidence module tells agent runs from certification runs** (re-plan §3.4; Annex E §2.3):

1. Separate logs. The evidence module (S4) reads only the gateway's exchange log in certification mode, never the masker's call log.
2. `caller` marking in Iridium's own log. The masker always sets `caller` to `agent.<short-jti>`; certification runs use the gateway's `gs.<tenant>.<user>` form (Annex D §2.8). `getIwsRequests` returns `caller`, so an extract can be split by prefix. The User Activity Report aggregates by IWS user and month and has no caller column (catalog `reports_library.md`), so it cannot separate agent calls; Annex D §2.8 says otherwise, so this is uncertain until verified on SITEST.
3. Quiet windows. Agent access is paused automatically for every CTO dry run (the two S5 dry runs and any rehearsal the CTO declares) and for the certification run: a window the CTO sets in advance with a start and end time, which the masker and the signer each enforce by themselves (§10). The evidence module checks that the `getIwsRequests` extract for the window holds no `agent.` caller, or it marks the run void.
4. One IWS user. Agents and the CTO share the single SITEST IWS user (CTO decision, 20 Oct 2026; no second user is requested), so `iwsUsername` never separates them and the User Activity Report for the month counts agent calls. The evidence index states that agent traffic shares the user and is separated by the `caller` prefix; whether agents are also paused for the whole calendar month of each certification-mode run is open (§17 #13).

## 10. IWS concurrency

- **The limit.** 2 concurrent requests per IWS user; the third gets "Too many connections!" (catalog Rules). Annex D assumes the limit is shared between the provisioning and reporting endpoints until Iridium confirms otherwise (Annex D §2.4).
- **Same permit system as the gateway.** S2 builds the gateway's permit module (§12) as a Postgres ledger in the masker VM's database. The signer container takes and releases permits; the masker reaches IWS only through the signer. One row per `(IWS user, slot 1..2)` with holder, lease expiry, fencing epoch and a cooldown time. Row-level security limits the signer's database role to the SITEST user's rows. Acquire is a conditional update; release clears the holder; a call cut off by timeout puts the slot in cooldown for 30–60 s, because IWS may still be working on it (Annex D §2.4, inferred there).
- **The masker's share: at most 1 of 2.** There is one SITEST IWS user (CTO decision, 20 Oct 2026). Agent traffic may only take **slot 2 (permit B)**, never slot 1 (permit A, reserved for interactive L0–L2 traffic; Annex D §2.4). So at most 1 agent request is ever in flight, and one slot is always free for the CTO's own live runs (manual calls and, from S3, the gateway prototype). The signer's HTTP connector to SITEST is also limited to 1 connection, so the transport cannot exceed its share even if the ledger is wrong. The signer also reads the pause, writes-off and window flags with its own read-only role: it refuses to take slot 2 while agents are paused or a CTO window is active, and refuses every write while writes are off, failing closed if the read fails. A missing pause row means paused and a missing writes row means off, in the masker and the signer alike, so a fresh database starts closed (tested).
- **Physical cap across processes.** Annex D's guarantee is physical: one process holds a pool of 2 connections (Annex D §2.4). From S3 the gateway prototype (connector limit 2; Annex F §6.1) shares the SITEST user with the masker. While the masker is enabled on that shared user, the gateway's SITEST connector limit is 1 (permit A only), so the physical cap stays at 2 across both processes; a test asserts it. The Compose file runs exactly one signer container (no replicas; a deploy stops the old container before it starts the new one) and the signer takes a Postgres advisory lock at start (the D2 pattern), so a deploy never runs two signer processes (re-plan §9 risk register). Where the S3 gateway prototype runs is decided in S3. It never holds a second copy of the SITEST secret on this VM: either it runs only in a CTO window with agents paused, like the harness (§12.4), or, if it must run beside the masker on the same user, it calls the signer for permit A, a signer change reviewed in S3.
- **Before the gateway runs.** In S2 the signer is the only automated SITEST client. The CTO's manual calls (SoapUI or the WSDL Explorer) do not use the ledger. Because agents hold at most one slot, the CTO's calls made one at a time never meet a third-connection rejection; a CTO who needs both slots pauses agents first.
- **Automatic pauses.** For every CTO dry run and for the certification run, the masker pauses agent access by itself for the window the CTO set in advance (§9): new agent requests get `403` with a pause code, and the signer itself refuses slot 2 for the window (above), so a masker bug or compromise cannot call during it. The pause starts early by the longest allowed method timeout plus the slot cooldown plus 1 minute, a constant a test asserts, so an agent call still in flight cannot overlap the window.
- **Per-session limits (*Inferred* defaults, configurable by the CTO):** 1 request in flight per token; 20 calls per minute; 1,000 calls per day; 20 writes per plan unless the plan sets fewer. A request that would wait more than 10 s for the permit fails fast with `IWS_BUSY`, `503` and `Retry-After` (Annex D §2.4 backpressure). Long-class methods (`getSpBalance`, raw usage, reports) are not in the S2 allowlist.
- **Daily budgets of distinct records (*Inferred*).** Calls per day alone would let a token copy the masked base (1,000 calls × 50 rows). So the masker also caps the distinct subscriber records issued: 500 per token per day (lower for `read:sp`, §17 #19) and 2,000 per day overall. A vault-growth alarm fires above the daily norm.
- **"Too many connections!"** is an alarm. Agents hold at most one slot, so when an agent call gets it, two other requests were in flight: the CTO's own calls (on Beta too, if Iridium counts the limit per user across SITEST and Beta; §17 #5), the gateway prototype, or a leak of the credential or the ledger. Check the CTO's own activity first (Annex D §2.5). Reads get one retry after a backoff; writes never.

## 11. Leak tests and runtime fail-closed

### 11.1 Detectors

| Detector | Rule | Source |
|---|---|---|
| IMEI | Any 15-digit run that is not a placed surrogate; Luhn not required (a valid Luhn digit only raises confidence) | [OW]: SBD/M2M+ IMEIs end in 0, and catalog examples fail Luhn |
| ICCID | 18–20 digits starting `89` with a valid Luhn digit, or any 19 digits, not a placed surrogate | [OW] 19 digits; `89` prefix and Luhn *Inferred* |
| IMSI | Any 15-digit run that is not a placed surrogate (overlaps IMEI; either hit blocks) | [OW] |
| MSISDN | 12 digits starting `8816` or `8817`; also `+` or `00` followed by those | [OW] |
| Phone numbers in text | E.164-like `+` and 8–15 digits | *Inferred* |
| Contract | `SUB-` + 7 digits or `SC-` + digits, not a placed surrogate | [MP], [OW] |
| Voucher serial | 19 digits, not a placed surrogate | [OW] |
| IPv4 / IPv6 | Any address that is not a placed surrogate (offline: any address outside `240.0.0.0/4` and `2001:db8::/32`) | — |
| Email | Any address that is not a placed surrogate (offline: not ending `@example.invalid`) | — |
| IMO / MMSI | 7-digit IMO with valid check digit; 9-digit MMSI | *Inferred* |
| Long digit runs | 9 or more consecutive digits in every string element, except placed surrogates and the operational fields of §11.4 | catch-all |
| Known values | Exact match of any real value seen in this call, including the injected auth values (§6.4) | — |
| Cross-call known values | Keyed-hash match of output word sequences against every real name-like value seen (§6.4) | — |
| Signatures | Any Base64 string of HMAC-SHA1 length (27–28 characters, `=` padding) anywhere in output | Catalog signature algorithm; length rule *Inferred* |
| Sensitive names | Elements named like the secrets in §5.1 with a non-`REDACTED` value | Annex D §2.8 |

**Exemption.** A value is exempt only if it is byte-equal to a surrogate the masker placed in this response (a per-response set). A value that merely looks like a surrogate, but that the masker did not place, is a hit. Offline scans, which have no such set, use the reserved prefixes (§11.3).

Detectors also run after Unicode normalization (NFKC) and base64 decoding of long base64-looking strings. Separator removal is limited to digit groups joined only by spaces, hyphens or dots that total 12–20 digits, and it skips ISO-8601 and `DD-MON-YYYY HH24:MI:SS` timestamps. So `9 9 0…`, full-width digits or encoded copies do not slip past, while timestamps and version strings do not trip a rule. Detectors use linear-time regular expressions (RE2 or bounded patterns), so no input can make them backtrack for long.

### 11.2 Per-response-shape tests from synthetic data

- For every allowed method, a test builds a synthetic response from the WSDL schema (every optional element present, arrays of 1 and 3, each account subtype by `xsi:type`, nil and empty variants) and fills every identifier field with **canary** values: real-format values from a documented canary range that is not a surrogate prefix, so the detectors fire on them. The test asserts that the masked output contains no canary, no detector hit, every secret `REDACTED` (or nil or absent, §6.1), the same element structure, and that it validates against the WSDL schema.
- A **log leak test** drives every error path with canary data and asserts that no canary reaches the application logs (§9).
- The same for requests: every allowed write with surrogates maps back to the canaries, and every refused case is refused.
- A **deny-list test** on every response shape: the list of secret element names and the real-format patterns must never appear in output.
- Property-based tests (Hypothesis) for the detectors, tokenization round trips, collision handling and check digits.
- File names contain `mask` or `leak` (`tests/masker/test_mask_*.py`, `tests/leak/test_leak_*.py`), so CODEOWNERS routes them to the CTO.

### 11.3 Fixture scanning before git

- `scripts/leak_scan.py` runs every detector of §11.1 over all text files in the repository, with fixtures under `tests/fixtures/` in strict mode. It allows reserved-prefix surrogates, and the canary range only under `tests/leak/` and `tests/masker/`; the masker's in-prefix counter (§6.2) also confirms that the canary range is absent from SITEST. In CI it scans every commit in the PR range, not just the working tree, so a value added and removed inside a PR is still caught. It refuses non-UTF-8, binary or compressed files under `tests/fixtures/`. It runs in `make security` (and so in CI) and in the pre-commit hook.
- gitleaks keeps scanning for secrets (`make security`, CI history scan), with a rule for the masker token prefix `gsm_` (§3.3); the same pattern is registered with GitHub secret scanning. Its regex rules cannot check Luhn digits, so identifier detection lives in `leak_scan.py`.
- Adding the script and the Makefile target changes gate configuration, which is on the mandatory review list.

### 11.4 Runtime detector: block and alarm

After masking and before responding, the masker runs the detectors over the masked response, including decoded embedded payloads. Detection is field-aware. Type detectors run on every element whose field-map class is an identifier treatment, F, N or unknown, and on every kept string element. Kept elements with an XSD numeric, date or boolean type, and kept elements listed in `overrides.yaml` as a version, size, count or operational ID (for example `iwsVersion`, `wsdlRevision`, project version fields, `cdrId`, `sessionId`, `requestId`, `transactionId`, `bulkRequestId`, `queueEntryId`), skip the IPv4, MMSI, IMSI and long-run rules; they are still checked against known values. Otherwise a version such as `22.2.0.1` (Annex E §1.4) would trip the IPv4 rule and disable `getSystemStatus`.

**Fail closed on every failure, not just on hits.** Bytes are returned only when every stage returns an explicit clean result. Any exception, a masking-budget timeout (2 s, *Inferred*), an unavailable vault, key file, database or signer, a failed revocation or pause-flag read, a non-SOAP body (such as an HTML error page), a response over 5 MB (*Inferred*), or a list with more rows than the request allowed gives `502 MASKING_BLOCKED` or `503`, never IWS bytes.

On any hit, or on an unknown element:

1. The response is **not** returned. The agent gets `502` with `MASKING_BLOCKED` and the call id.
2. An incident row is written with the element path and detector id, never the value.
3. An alarm event (code and count, never a value) reaches the CTO at once through the alert channel (§14.4).
4. The method is disabled for all agents until the CTO re-enables it. Three blocks within an hour pause all agent access (*Inferred* thresholds).

Nothing raw is kept for debugging. No token scope or mode disables masking, the CTO's tokens included. If the CTO needs the raw response, the reproduction happens only on the CTO's trusted machine, outside the masker; the fix is then verified through the masker.

### 11.5 Red-team cases (part of the S2 test suite)

1. IWS error text that echoes a request value (`accountSearch` with a wrong filter type; `setSubscriberAccountStatus` on a missing account).
2. Escaped XML in `getIwsRequests` and `getQueueEntry` that contains other callers' requests, including `signature` and `callerPassword`.
3. Every account subtype through `getSubscriberAccount`, with identifiers in subtype-only fields (Certus voice lines, OpenPort phone lines, Paging `isdna`, vessel links).
4. Identifier variants: leading zeros, spaces, hyphens, `+` and `00` prefixes, IMEISV (16 digits), 14-digit IMEI without check digit, an SBD IMEI ending in 0 with an invalid Luhn digit, 20-digit ICCID, a real 12-digit number starting `99`, IPv6, mixed-case emails, full-width digits, values split across elements.
5. Free text and names containing identifiers and prompt-injection text; a name seen in a structured field in an earlier call, echoed in free text.
6. Enumeration: an agent sends guessed surrogates in the reserved prefix. Most guesses fail with `IDENTIFIER_NOT_ISSUED`, and issued surrogates outside the token's read scope get the same answer; the `IDENTIFIER_NOT_ISSUED` rate alarms above a threshold (*Inferred*); rate limits and daily budgets hold.
7. An agent tries to write a real-format identifier into `spReference` or `description`.
8. Operation-name and parser tricks: wrong case, a root element that differs from the path, a Content-Type `action` mismatch, two operations in one body, auth fields in the request, a `caller` set by the agent, duplicate `newStatus` or `accountNo` elements, a comment-split enum (`DE<!---->ACTIVE`), ` DEACTIVE `, `Deactive`, full-width text, `wsa:ReplyTo` and other SOAP headers, `xsi:type` substitution.
9. Endpoint tricks: Beta or production host names in headers, URLs or XML; redirects from the IWS side (never followed).
10. XML attacks: external entities, entity expansion, huge documents, deep nesting (parser with entity resolution and network access off and size and depth limits).
11. DEACTIVE through every path: `newStatus` DEACTIVE or CLOSED, `accountStatus` in `accountUpdate`, `bypassQuarantine` with any value but `FALSE` (`FALSE` is accepted), a plan that lists DEACTIVE (must fail to load), bulk methods, `activateSubscriber` with `bulkAction` `TRUE`, a `*BulkDetails` element or a `BULK` device value, the same requests under a CTO token.
12. Token tricks: expired, wrong key, `none` algorithm, an `HS256` token, a `jku`/`x5u`/`jwk` header, read scope used for a write, a revoked `jti`, a plan id in the header that differs from the token.
13. Concurrency: 5 parallel agent requests never put more than 1 in flight to SITEST; a gateway-held slot is never taken; with agents paused, a CTO window active or the pause row missing, the signer refuses slot 2 even when the masker asks for it, and with writes off or the writes row missing it refuses every write.
14. `background=TRUE` on `createOnDemandReport` and every other always-refused method.
15. No false blocks: `getSystemStatus` and `getProjectVersion` with versions such as `22.2.0.1`, a kept 9-digit count, and a `statusDescription` holding a space-separated timestamp are not blocked.
16. Search oracles: prefix walking on `getVessels.vesselName`, `NOT_EQUAL` and `CONTAINS` on `accountSearch`, a name search on `getSubscriberOrganizations`, login guessing on `getQueueEntries.createdBy`: all refused or overwritten.
17. Egress from the containers: from the masker container every outbound connection fails with network unreachable (`1.1.1.1:443` for DNS over HTTPS, the SITEST address, an object-storage host), and neither `iwstraining.iridium.com` nor a random label under a Globalsat domain resolves; from the signer container everything but the pinned SITEST address on 8443 fails, including `1.1.1.1:443`, and the same names do not resolve; from `backup`, `alerter`, `admin`, `retention` and `postgres`, a connection to the signer fails; `169.254.169.254` (the provider metadata service) is unreachable from every container; Caddy and the helpers reach only their allowlisted names through the egress proxy, and their name-resolution result is recorded. The Beta and production names are checked only by the CTO, by hand (§15.1 #4), so they appear in no test or code.
18. Fail closed: an exception inside masking, a masking timeout, the vault key file, the database or the signer unavailable, a failed revocation read, an HTML error page from IWS, an oversized response, and a list with more rows than requested all return `502` or `503` and no IWS bytes.
19. Bulk pulls: `numResults` 0, `limit` 0, a blank `getSubscriberOrganizations` `Id`, `startRow` beyond the cap, an unfiltered `accountSearch` without `read:sp`: all refused; the daily distinct-record budgets hold.
20. A signature-length Base64 string in fault text, and an `iwsLogImpl` entry from another caller, never reach the agent.
21. Write scope after a simulated SITEST refresh: a derived account whose device is no longer test inventory is refused; an `accountUpdate` that changes a field not in `mutable_fields`, or writes `REDACTED` back, is refused.
22. Forged writes from the masker side: a `setSubscriberAccountStatus` to `SUSPENDED` or an `accountUpdate` on a contract that is neither signed test inventory nor a derived account the signer recorded, sent straight to the signer with a valid link token, is refused by the signer; so is a write over the plan's budget, after its expiry, under an unsigned plan, or while writes are off.

### 12.1 How the masker calls SITEST before the gateway exists

**Decision: option 2.** The signer core is small (UTC timestamp, HMAC-SHA1 over operation name plus timestamp, Base64; Phase 1 plan §1.3; Annex D §2.3) and S3 needs it anyway. D1 is not closed yet. If fallback A replaces the gateway with a plain-Java service (Annex F §6.3), the masker either keeps the Python signer core as its own SITEST client (a second signer, which needs a `CLAUDE.md` change) or calls the gateway service over the Annex D §2.1 interface; decided at G1.

**Signer isolation (accepted, §17 #17).** The signer runs in its own Compose container. Compose injects the SITEST secret file into that container only (§13.1); the masker container never has it, and has no route off the VM (§3.2). The masker calls the signer over the `link` network, authenticated by the link token, with the Annex D §2.1 interface; the signer's HTTP service listens only on its `link` address and refuses any other caller (§3.1). The signer re-checks the allowlist and the DEACTIVE and bulk blocks, injects auth, holds the permits, sends to the pinned address and returns the IWS response with the signed timestamp for the call log, never the signature. Before returning, it replaces any echo of the signature in the response with `REDACTED`. At start it gives the masker `iwsUsername` and the SP account numbers, which are identifiers the masker must mask, not the secret key (§4.1, §6.4).

**Write guard in the signer (S2b).** Write scope is enforced a second time where the secret is, so a compromised masker cannot write outside test inventory. For each write, the signer, with its own read-only database role and failing closed if any read fails: verifies the plan's signature and the signed inventory rows against the plan-approval public key baked into its image; checks that the plan is in its validity, not revoked, and lists the method with its constraints; checks that every identifier field in the final bytes (from the guard's own constant list of the device, contract and e-mail paths of the allowed write methods, independent of the masker's field map) holds a value whose HMAC under the inventory key matches a signed row named in the plan, a contract the signer itself recorded from an `activateSubscriber` success on such a row, or one of the plan's `allowed_literals`; counts the write against `max_writes` in its own ledger rows; and refuses while writes are off, agents are paused or a CTO window is active (§10). Its recorded contracts expire with the plan and are cleared when the signer itself sees a SITEST version change in a `getProjectVersion` or `getSystemStatus` response. Residual risk: while it is compromised, a masker can still make allowlisted reads within the one permit, and allowlisted writes on an approved plan's test inventory within its budget; it cannot take the secret to Beta without a container escape (§2.2).

## 13. Secrets and keys

No AWS service holds a masker secret or key in S2, and no AWS credential is ever placed on the VM. Secrets and keys on the VM are root-only files encrypted at rest with sops and age. Each is decrypted only into the container that needs it (admin secrets only on demand, §13.2), and Keeper holds the CTO's custody copy of each. Root on the host can read every decrypted file and every container's memory; that case is a Sev1 (§2.2, §14.4).

### 13.1 The SITEST secret

- **Storage.** One sops file on the VM (`/etc/airtimesat/secrets/signer/sitest.enc.yaml`, owner root, mode 0600) holds `iwsUsername`, the secret key and the SP account number(s). The CTO encrypts it on the trusted machine from the Keeper record to the VM's age public key and copies only the encrypted file to the VM, so the plaintext never touches the VM's disk. Never in git, Terraform, a cloud-init file, an image or an environment variable.
- **Injection.** At start, a root systemd unit (`airtimesat-secrets`) decrypts the sops files of the long-running containers into tmpfs (`/run/airtimesat/<container>/`, each file mode 0400 and owned by that container's own UID, §14.1), then shreds the age identity from tmpfs (§17 #22). Admin secrets are not decrypted at boot (§13.2). Compose mounts the SITEST secret into the `signer` container only, as a Docker secret file that `common/secrets_file.py` reads (§12.2). The masker, Caddy, Postgres and helper containers never see it. The signer reads it once at start and holds it as a `SecretValue`. Each signer start raises an alarm (§14.4); unlike the Secrets Manager read alarm of the AWS design, a root reader of the file or of the signer's memory is not seen.
- **No Beta copy anywhere.** The same credential works on Beta, so a copy under a "beta" name would add nothing but a second copy.
- The secret never reaches an agent session, a document, a log or git. Error messages name the secret, never its value (existing `SecretNotAvailableError`).
- **Rotation and compromise.** Rotation is manual (`resetIWSUserPassword` returns the new secret in clear text; dual-control runbook, Annex D §2.5) and is never available to agents. On suspected compromise: kill switch (§14.4; step 6 if the host itself may be compromised), ask Iridium to rotate (procedure and lead time still to be obtained; re-plan §11.1 Q4), re-encrypt the new value from Keeper, restart the signer. A SITEST secret leak is also a Beta leak, so the CTO treats it like a Sev1 (re-plan §8.1).
- The production gateway (S4) is unaffected: it stays in AWS and reads IWS secrets from Secrets Manager (`modules/secrets`), decided in S4.

The masker therefore holds what it needs to mask (`K_mask`, the vault key) but no key that approves anything: token and plan signatures are checked against public keys, and the private keys never leave the trusted machine (and Keeper). The vault key and `K_mask` together are the crown jewels (§2.1). On the VM they exist in the masker's memory and tmpfs mount, in the admin container while it runs, and in the sops files. Root on the host can read them. Without KMS, they also sit in the internet-facing masker process, whose responses to agents are a channel out even though the container has no egress; this residual risk is recorded in §17 #20. Their custody is Keeper plus an offline escrow of the backup key, `K_mask` and the vault key (a sealed copy with a named custodian, or a Keeper break-glass record), so a future deputy can recover the backups if the CTO loses Keeper access (§17 #26).

Rotation: the token key can be replaced at any time by rebuilding the masker image with a new public key and redeploying it (all tokens die, which is also a kill switch). Replacing the plan key invalidates every loaded plan and every signed inventory row, which the CTO then re-signs after rebuilding the masker and signer images. The age identity is rotated by re-encrypting the sops files to a new recipient. The link token, the database passwords and the object-storage keys are rotated on any suspected host compromise (§14.4 step 6). `K_mask` is not rotated in normal operation (§6.3); after a suspected vault or key compromise the CTO generates a new one, which re-surrogates everything, and old fixtures are regenerated.

### 13.3 Making Beta unreachable although the credential works there

There is one IWS test user, and its credential works on SITEST and Beta (CTO decisions, 20 Oct 2026). The masker side alone must make Beta unreachable, in layers, so that no single mistake reaches it:

1. **No Beta in the code.** The only IWS endpoints the signer can load are the two SITEST constants and the pinned SITEST address in `gateway/endpoints_sitest.py`. Beta and production URLs do not exist in any module the masker or the signer imports (`masker-sitest-only`, §12.3). There is no endpoint setting, environment variable or header that changes the destination. A test fails if any `iridium.com` host name other than `iwstraining.iridium.com` appears anywhere under `src/` (from S4, except in `gateway/endpoints_production.py`, which `masker-sitest-only` keeps out of the masker's reach) or under `infra/masker-vm/`, so the test itself names no Beta or production host. Those names appear only in the CTO's manual check, in a runbook under `docs/runbooks/` (§15.1 #4), never in code, tests or configuration.
2. **Pinned host and address in the transport.** The signer connects only to the reviewed SITEST address, sends SNI and `Host` for `iwstraining.iridium.com`, verifies the TLS certificate for that name, follows no redirects, and checks before each send that the URL host equals the SITEST constant. If Iridium moves SITEST, calls fail and alarm until the CTO reviews and pins the new address; that is the intended failure.
3. **No DNS where it matters.** No container has a working resolver (§3.2), and the masker has no network off the VM. The startup self-test refuses to start unless, from inside the container, `iwstraining.iridium.com` and a fixed random label under a Globalsat domain both fail to resolve (the signer connects by pinned address, so if even the SITEST name fails, no name resolves), and a TCP connection to a fixed test address (TEST-NET-1, `192.0.2.1:443`) fails at once: reset by an nftables `reject with tcp reset` rule for the signer, network unreachable for the masker. A failure raises an alarm. The egress-drop alarm excludes only that test address, so every start does not trip the alarm that guards Beta.
4. **Egress firewalls.** The host firewall allows the signer's subnet TCP 8443 to the pinned SITEST address only, and drops and logs every other container egress (§3.2). The provider cloud firewall allows the VM TCP 8443 to the same address only. A dropped packet from the signer or a helper raises an alarm. The masker has no route, so its attempts fail without reaching the firewall (tested, §11.5 #17). If Beta listens on 443, the cloud firewall's broad 443 rule does not stop it; the host firewall and the proxy allowlist do, and layers 1–3 still apply (§15.2 step 2 records Beta's address and port). Both rule sets change only through a reviewed PR to `infra/masker-vm/` and a CTO run.
5. **Shared addresses.** Whether SITEST and Beta share addresses is not known; the CTO's resolution check (§15.2 step 2) records both. If they share an address, layers 1–3 carry the control: the signer sends only the SITEST name and accepts only its certificate. If they also share a wildcard certificate, the SNI and `Host` constant is the only separation.
6. **The secret stays in the signer.** Only the signer container holds the credential (§13.1; from S3 also the CTO-started harness during its window, §12.4), so the internet-facing masker process never has anything it could take to Beta. No second, SITEST-only user is requested.
7. **Review.** Every layer sits on the mandatory review list (gateway, masker, `infra/`, Dockerfiles).

### 13.4 The trusted machine

The trusted machine is the one CTO device that holds key material and raw data off the VM. It uses the token-signing, plan-approval, inventory, VM age and backup keys; encrypts the SITEST secret; builds and scans the images; holds the raw ST-03 sample; and makes the CTO's own IWS calls, DEACTIVE included. It takes over what KMS gave the AWS design (non-exportable keys, MFA, a log entry per signature), so it is defined here:

- **One named device** ([FILL: which device]) with full-disk encryption, automatic OS updates and a screen lock.
- **No AI agent on that user.** No AI agent, coding assistant or agent CLI runs under the OS user that holds Keeper and SSH access. Admin SSH sessions run in a terminal no agent can read, because `plan show` prints the last 4 digits of test-inventory values and the CTO's live calls return raw data.
- **A minimal offline tool.** `keys init`, `mint`, `plan sign` and `inventory sign` ship as a separate entry point, `masker_offline`, whose import graph is only `cryptography`, `pyyaml` and `common.plan_format` (plus one PIV library with hardware keys), enforced by the `offline-minimal` contract (§12.3) and installed from the reviewed commit in its own venv with pinned, hash-checked dependencies. The platform's other dependencies (lxml, asyncpg, fastapi, aiohttp) never load next to a signing key.
- **Hardware keys (recommended, §17 #27).** The token-signing and plan-approval keys are non-exportable P-256 keys on a hardware key (PIV, touch required for each signature). Losing it means a rotation (§13.2), not a recovery. The VM age identity, the backup key and the masker keys stay software keys in Keeper, because they must reach the VM or be escrowed.
- **A local log.** Every mint and every plan or inventory signature is appended to a local log. The daily digest (§14.4) lists the time of each new `jti`'s first use (a time, not the `jti`), and the CTO matches the times with the log (and, on a mismatch, reads the call log's `jti`s over SSH); a `jti` the CTO did not mint means the signing key is compromised.

### 14.4 Monitoring, alarms and kill switch

**Alert channel.** CloudWatch, CloudTrail and SNS ran outside the workload; here every alarm and log starts on the VM it watches, so two paths leave it. First, the `alerter` container reads alarm events and the admin log from Postgres with its own read-only role and forwards each as an enumerated code (a `CHECK` constraint on the alarm table lists them), a bucketed count (1, 2–9, 10+) and a time, never a value or a free-form field, through the egress proxy to one authenticated, private endpoint (§17 #25). So a compromised masker cannot encode identifiers in alarm counts. It deduplicates and rate-limits per code, sends noise codes (token-failure bursts, 5xx rate, container restarts, the first use of a new `jti`) in a daily digest, and keeps quota in reserve for the critical codes (leak, DEACTIVE, egress drop, SSH login), so a scanner flood cannot use up a free tier. It also sends a heartbeat every 5 minutes to a dead-man's-switch service, which e-mails the CTO if the heartbeat stops: VM down, alerter down or disk full. Second, `airtimesat-hostwatch`, a host systemd unit with no database access, posts host events straight to the alert endpoint through the proxy: an SSH session opening (by `pam_exec`, before the session can act), `sudo` use, the nftables drop prefix, a failed unattended upgrade, a pending reboot older than 72 hours, disk over 80%, a Docker or firewall restart. It also ships auth, `sudo`, Docker-event and nftables logs in near real time to an append-only bucket (write-only key, object lock where supported; 90 days), so a root intruder cannot erase what was already sent. The provider's agentless and billing alerts are a third, independent path.

**Admin actions.** Every admin action is written to the append-only admin log (§9). Un-pause, writes on, a window removed, a revocation cleared and every export raise an alarm.

**Alarms (to the CTO):** runtime detector block (any); unknown element (any); log-filter leak hit (any); DEACTIVE or always-refused attempt (any); `IDENTIFIER_NOT_ISSUED` burst; daily distinct-record budget or vault growth; "Too many connections!" (any); IWS `AUTH` fault (any: wrong or rotated secret, or clock skew); clock skew over 5 s; egress drop from the signer or a helper (any but the self-test address); signer start (each start reads the secret); startup self-test failure; a signer refusal of a write (§12.1); successful SSH login or `sudo` use (hostwatch, any); the admin actions above; token verification failures burst (digest); first use of a new `jti` (its time, in the digest, §13.4); 5xx rate; container restarts; vault occupancy over 50%; in-prefix real value (§6.2); backup failure or a backup older than 26 hours; certificate expiry within 14 days; disk over 80%; failed unattended upgrade; pending reboot older than 72 hours; heartbeat missing; provider billing alert.

**Kill switch.** The first two need only the provider console or API, so they work even if SSH, the database or the VM itself is broken:

1. Remove the inbound 443 rule from the provider cloud firewall, then stop caddy (or run step 3) to drop established connections, because cloud firewalls are stateful.
2. Power off the VM in the provider console. This also stops every IWS call.
3. `masker-admin pause` over SSH sets the global flag: every agent request gets `403`, and the signer refuses the agent slot; permits are released. Per-method and writes-only flags exist too. Writes start **off** in every deploy. Revoking single tokens (`jti`) or all of them (the "not before" time) works the same way.
4. Stop the signer container and wipe its tmpfs secret file, so even a running masker cannot reach IWS.
5. Deploy a masker image with a new token public key: every token dies, even if the database is lost.
6. **Suspected host compromise.** Power off; treat it as a Sev1 and ask Iridium to rotate the secret; destroy the VM; rebuild from git, Keeper and the last backup taken before the suspected time; apply the restore runbook (§14.3); rotate the age identity, every database password, the link token and the object-storage keys; rotate `K_mask` only if the vault or the masker's memory could have been read, because that re-surrogates everything (§13.2).

Automatic trips: a runtime block disables the method; three blocks in an hour pause everything; a CTO dry run or the certification run pauses agents for its window, in the masker and in the signer (§9, §10).

## 17. Decisions and open items

On 20 Oct 2026 the CTO accepted the recommendations of the first draft and took the hosting and IWS-user decisions in the change note above. This list records them as decisions, rewritten where the VM changes them, and adds what the security review of the VM design raised. The numbers are kept so that references elsewhere stay valid. Items marked **Open** still need the CTO (and, where named, Legal).

1. **Agent access path. Decided:** an HTTPS endpoint (Caddy on the masker VM) with CTO-minted session tokens, signed ES256 with a key held off the VM (a hardware key recommended, #27) and used only on the trusted machine (§3.3, option A; §13.4). Not mTLS, a tunnel or an overlay in the session.
2. **Hosting and run cost. Decided (CTO, 20 Oct 2026):** one VM with Docker Compose. DigitalOcean is the reference and Hetzner the alternative, with no AWS service for the S2 masker. The CTO's target was about US$12–25/month; the honest estimate is about US$24–31 on DigitalOcean at the recommended 2 vCPU size and about US$10–15 on Hetzner (*Inferred*; §14.2), so the reference comes in a few dollars above the target unless the 1 vCPU size proves enough. This replaces the earlier ECS Fargate and ALB recommendation (about US$105–125/month) and saves about US$75–100/month. The production gateway (S4) stays in AWS and is decided then.
3. **Masking scheme. Decided:** keyed tokenization with a vault and reserved-prefix surrogates (§6.6). Not FF1.
4. **How the masker calls SITEST. Decided:** S2 builds the gateway signer core and permit ledger, run as the signer container and reached through `gateway.sitest_port`, with the contract and `CLAUDE.md` changes of §12.3.
5. **IWS users. Decided (CTO, 20 Oct 2026):** one SITEST IWS user; no second user is requested from Iridium. The masker makes Beta unreachable on its own side (§13.3), holds at most 1 of the 2 concurrent request slots so the CTO's own live runs keep the other (§10), and pauses agents automatically during the CTO's dry runs and the certification run (#13). The withdrawn recommendation asked Iridium for a second, agent-only user. Follow-ups in `Globalsat-Group/IWS`: a note on Annex D §2.4 and §2.9, whose separate SITEST users (`gs-cert`, `gs-ci`) no longer exist, and an Annex B question on whether the 2-request limit counts per user across SITEST and Beta. Until Iridium answers, the CTO treats a Beta call like any other own call: one at a time, or with agents paused.
6. **Raw usage and inline reports for agents. Decided:** refused in S2. For ST-08 in S3, a metrics-only mode (the masker makes the call and returns row counts, sizes, parse time and field presence, no rows) for both the 10,000-row raw-usage page and the 5,000-row `accountSearch` (§12.4). Masked rows, with coordinates generalized, are considered only after S2a has run clean.
7. **`CLOSED` treated like DEACTIVE, and the CTO's DEACTIVE path. Decided:** `CLOSED` is hard-blocked for every token, because it is terminal. The CTO's own DEACTIVE: a manual call from the trusted machine with agents paused, recorded with `masker-admin note` (§8.5).
8. **Retention. Decided as the working periods; final periods Open with Legal:** call log 18 months; masked exchanges 90 days; vault values deleted 90 days after last use, with the slot kept forever as a tombstone; test-inventory rows never expire; encrypted backups 30 days (§9). Legal sets the final periods per country and confirms the basis for masked data in agent transcripts.
9. **S2 split and budget. Decided, re-baselined on 20 Oct 2026:** S2a (reads) and S2b (writes), same scope, 19 / 30 / 42 CTO-hours (*Inferred*; 25.5 expected before the security review), with about 2 h moved out of S3 and ST-15 back in S3 (§16). S2a exit expected in week 6. S3 is re-baselined before its work starts.
10. **WSDL snapshot and field-map location. Decided:** the snapshot comes forward from S3 to S2 under `gateway/wsdl/`, with the generated field map under `gateway/wsdl/fieldmap/` (§12.2), subject to the interim confidentiality rule (re-plan §8.6).
11. **Endpoint name and certificate. Open.** Recommend a dedicated subdomain such as `masker.<globalsat-domain>`, with an A record to the VM's static IP. For the certificate, Caddy sees every token and masked response, so the trade-off is: (a) an automatic certificate from Caddy through the TLS-ALPN challenge on 443, with Caddy's only egress the ACME certificate authority through the allowlisting egress proxy (#25): no CTO time, and the internet-facing process keeps one narrow path out, to the CA's servers only, which is not a useful exfiltration path; (b) Caddy with no egress at all, with a certificate the CTO obtains on the trusted machine (by DNS-01, which needs API access to the zone, or from a commercial CA, valid at most 200 days since March 2026, general knowledge) and installs by hand, about every 60 days (Let's Encrypt) or twice a year. Recommend (a). Who controls Globalsat's DNS zone? [FILL]
12. **Token lifetime and delivery. Decided:** read tokens 4 h, write tokens 2 h or less (8 h if minting twice a day is too much); minted on the trusted machine; set by the CTO in the dedicated SITEST cloud environment, as a Network secret if that keeps the value out of the session, otherwise as `MASKER_TOKEN`; never pasted into chat (§3.3). Minting takes a few minutes each time (*Inferred*), counted in S3 CTO-hours. Key-bound (DPoP-style) tokens are not in S2a; revisit if a token ever appears in a log, a transcript or git.
13. **Automatic pauses. Decided:** agents are paused automatically, by the masker and by the signer, for every CTO dry run (the two S5 dry runs and any declared rehearsal) and the certification run. The evidence module voids any window that shows an `agent.` caller. **Open:** because agents share the one IWS user, the User Activity Report for the month counts agent calls. Either the evidence index states this and separates the traffic by the `caller` prefix, or agents are also paused for the whole calendar month of each certification-mode run. Recommend the statement plus the caller-prefix split, because a month's pause would stop agent work for weeks; ask Iridium whether that satisfies its certification team (Annex B).
14. **Database and isolation from production. Decided, rewritten for the VM:** Postgres runs as a container on the masker VM, with its data on a block-storage volume, for the masker, the vault, the test inventory, the plans and the SITEST permit ledger. No RDS. The masker VM never shares a host, a database or a database role with anything that holds a production credential, and it does not share the Hub droplet. The production gateway (S4) gets its own database in AWS, decided then.
15. **Plan location. Decided:** `test-plans/` in this repository, reviewed by PR, loaded only with `masker-admin plan show`, `masker_offline plan sign` (on the trusted machine) and `masker-admin plan attach`. Add the path to CODEOWNERS.
16. **Admin path. Decided in principle; the way SSH is opened Open.** SSH with FIDO2 hardware-backed keys only, no passwords and no root login, and admin commands run in the one-off admin container (§14.1, §14.3). The provider's guest agents are removed, so the recovery console is the only break-glass access (§14.1). **Open:** (a) SSH closed in the cloud firewall by default; the CTO adds the current address for each session from the trusted machine (`doctl compute firewall add-rules`) and removes it afterwards; or (b) a private overlay (Tailscale or WireGuard) with SSH closed to the internet, whose coordination and relay hosts then join #25. Recommend (a): it works from changing networks and adds no third party or agent on the VM. Also confirm FIDO2 as mandatory (recommended; it needs a hardware key, two with a spare, about US$50 each, general knowledge), which was only recommended before.
17. **Signer isolation. Decided:** a separate Compose container, the only one that holds the SITEST secret and the only one with a route to SITEST. It is reachable only from the masker, over the `link` network with the link token (§3.1). It re-checks the allowlist, the DEACTIVE and bulk blocks and the pause flags, enforces write scope itself from S2b (signed plans, signed inventory, its own budget count; §12.1), holds the permits, and never returns the signature. The ECS-specific options of the first draft no longer apply.
18. **Spike-test harness. Decided:** a harness in S3, run as a one-off container that the CTO starts over SSH only inside a declared window with agents paused, returning fault codes and timings only, so that ST-02 negatives, ST-05 and the ST-07 "Too many connections!" case run without opening the masker's rules or the signer's 1-connection limit (§12.4). Its review (about 1–2 CTO-hours, *Inferred*) is S3 scope.
19. **Read scopes for agent tokens. Decided:** agent tokens default to `read:catalog read:inventory`. The CTO mints `read:sp` (SP-wide, with a lower daily budget, for example 200 records, *Inferred*) only for S3 tests that need SP-wide data, such as ST-03's "every account type present".
20. **`K_mask` custody and surrogate epochs. Decided, rewritten; residual risk Open.** The accepted option of a KMS HMAC key that is never exported no longer applies (no KMS). `K_mask` is generated on the trusted machine, kept in Keeper and the offline escrow, and present on the VM as a sops file, in tmpfs and in the memory of the masker (and of the admin container while it runs) (§6.3, §13.2). No epochs in S2; revisit with Legal's retention answer. **Open:** `K_mask` and the vault key now sit in the internet-facing masker process, and its responses to agents are a channel out even though it has no egress. Either accept this as a residual risk for S2, or add a small `keyholder` container on its own internal link with the masker, holding `K_mask` and the vault key and exposing only derive, encrypt and decrypt, with per-minute caps and the vault-growth alarm (about +1 CTO-hour, *Inferred*). Recommend accepting it for S2 and revisiting before any production use.
21. **Device swaps. Decided:** out of S2b (§4.3). If a later test needs them, add a CTO-confirmed class: the plan lists each {from, to} pair under `irreversible:` with a dry run required, and the send needs a second CTO approval (`masker-admin approve-call <call-id>`). Record the old device's state in ST-04 first.
22. **Unlocking secrets at boot. Open.** (a) The VM age identity stays only in Keeper. After each reboot the CTO pastes it over SSH into tmpfs; `airtimesat-secrets` decrypts the container secrets and then shreds the identity, so it is off the VM's disk and in memory only during unlock. Automatic reboots are off, and the CTO reboots in a weekly maintenance window, and within 72 hours for a critical kernel, runc or containerd fix (§14.1). (b) The identity is a root-only file on the VM, so the VM restarts unattended. Recommend (a): a disk snapshot, a provider backup or someone with provider-side disk access then gets nothing usable, a root-password reset from the provider panel reboots the VM and finds nothing to read (§14.1), and a locked masker fails closed (agents simply wait). Neither option protects against root on the running VM, which can read the decrypted files (§2.2). Cost: a few minutes per reboot (*Inferred*), counted in later stages' CTO-hours (§16.1).
23. **Provider account isolation. Open; a precondition of §15.2 step 5.** Recommend: the masker VM in a DigitalOcean team (or Hetzner project) where only the CTO is a member, with 2FA by a hardware key on the provider login, separate from any team in which other people administer the Hub. Anyone in the team can open the VM's console, snapshot it or change its firewall. The provider API token stays in Keeper. No secret reaches the VM until this holds.
24. **Data protection at the new provider. Open, for Legal.** The vault, which holds real SITEST identifiers (encrypted), the call log and masked exchanges (pseudonymized personal data) and their backups would sit with the hosting provider, in the region chosen in §15.2 step 2 and in the backup region (§14.3). Legal's data-protection task must cover that provider in both regions: its DPA, sub-processors, data location and the cross-border transfer of the personal data of subscribers in the countries SITEST holds. The alert and heartbeat services receive only enumerated codes, bucketed counts and times, and the security-log bucket holds host logs only, with no personal data. Recommend: Legal confirms before the recording session (§15.2 step 8), the first time real SITEST data reaches the VM; until then, only system calls go through the masker.
25. **Outbound destinations beyond SITEST, DNS, NTP and registries. Open.** Images no longer come from a registry (§14.3). Every 443 destination goes through the host egress proxy, each allowed only for the one container or host service that uses it, never for the masker container: the provider's apt mirror (the host); the ACME certificate authority (Caddy, if certificates are automatic, #11); one alert endpoint and one heartbeat service (the alerter and hostwatch, §14.4); object storage for the off-site backups and the host security logs (the backup job and hostwatch, §14.3, §14.4); and the NTS time servers on TCP 4460 (chrony, §3.2). Recommend allowing these and dropping the provider's metrics agent: hostwatch reports disk and the heartbeat reports a dead VM. The alert channel must be authenticated and private (no public topics), delivering to a CTO-only mailbox or device that no agent connector can read; the heartbeat URL is a secret (sops, alerter only). **Open:** which alert service (an e-mail API or a push service) and which heartbeat service. [FILL]
26. **Backups. Decided (encrypted backups, CTO 20 Oct 2026); details as recommended, replacing RDS backups; tamper protection Open:** a nightly `pg_dump`, streamed through age with no plaintext temporary file, to object storage in another region of the same provider, kept 30 days (*Inferred*), restore tested at the S2a exit and quarterly, with the restore runbook (§14.3). Provider VM snapshots stay off. Under #22 (b) they would hold the unlock key next to the encrypted files. The backup key, `K_mask` and the vault key are escrowed offline (a sealed copy with a named custodian, or a Keeper break-glass record) so a deputy can recover (§13.2). **Open:** a compromised VM holds the upload key. DigitalOcean Spaces keys appear not to be write-only without delete (to verify), so the VM could delete every backup. Recommend object versioning plus object lock with 30-day retention; if the reference provider cannot provide it, put the backup and log buckets with a provider that can (Hetzner Object Storage, to verify) and add it to Legal's review (#24), or have a CTO-only second machine pull the backups.
27. **Hardware keys on the trusted machine. Open.** Recommend: the token-signing and plan-approval keys as non-exportable P-256 keys on a hardware key (PIV, touch required), with the FIDO2 SSH key of #16 on the same device and a spare; losing it means a rotation, not a recovery (§13.2, §13.4). The alternative is software keys in Keeper, loaded only by the minimal offline tool. About 0.5 CTO-hour of setup, inside the trusted-machine line of §16.1 (*Inferred*).
